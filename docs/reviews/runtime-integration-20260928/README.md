# 앞단·개인정보 파기·실험 스크립트 통합 점검

2026-09-28. #258·#251·#249를 로컬 통합한 상태의 검사다. 실제 맥미니 부하나 모델 응답 품질을 새로 측정한 결과가 아니다. 임시 SQLite·합성 사건·외부 네트워크 차단 조건이며 유료 호출과 운영 데이터 변경은 없다.

## 확인한 충돌과 수정

1. 자동 파기는 사건마다 VACUUM을 실행하고 회차 마지막에 또 실행했다. 이번 회차의 삭제를 모아 **실제 삭제가 있으면 마지막에 한 번** 실행한다. 빈 회차는 실행하지 않는다. 일부 처리 후 예외가 나도 삭제된 자료의 정리는 수행한다. 다른 스레드의 명시적 정리는 별도로 보존한다.
2. 여러 작업의 최초 DB 연결과 저장소 캐시 복원이 겹칠 수 있었다. 단일 초기화와 완전한 로드 후 공개를 보장하도록 잠금을 적용했다. DB 쓰기가 실패했을 때 메모리에서만 성공한 것처럼 보이던 순서도 수정했다.
3. 초기 K 해석을 모의 응답으로 지연시키고, 실제 임시 SQLite를 쓰는 프로필 조회 API가 지연 해석과 독립적으로 응답하는지 확인했다. 해석 중 프로필 삭제 후 응답이 돌아와도 메모리와 재조회한 DB에서 복원되지 않았다.
4. 개인정보 스케줄러가 한 번만 시작하고 종료 요청으로 멈추는지 확인했다. 초기 개인 해석 큐와 파기 스케줄러는 별도 스레드이며 모델 대기 중 저장소 잠금을 잡지 않는다.
5. backend/app 전체의 Python import 구문을 검사한 결과 experiments를 가져오는 런타임 경로는 없었다. #249는 향후 실행할 스크립트와 과거 산출물 보존용이며 이번 머지가 실험을 예약하거나 실행하지 않는다.

## 로컬 저장소 부하 검사

반복마다 새 SQLite에 만료 사건 100건과 비교용 자료 약 400KiB를 넣고, 파기와 독립 저장·조회 200회를 두 스레드에서 동시에 실행했다. 변경 전후 각각 3회, 모두 100건 삭제와 200회 저장 결과를 검증했다. 도로망·모델·서버 API 실호출은 없었다.

| 항목 | 변경 전 | 변경 후 |
|---|---:|---:|
| 회차당 전체 DB 정리 횟수 | 101 | 1 |
| 100건 파기 회차 시간 범위 | 562~816ms | 263~365ms |
| 동시 저장·조회 p95 범위 | 0.52~2.37ms | 1.99~2.39ms |
| 쓰기 오류·저장 누락 | 0 | 0 |

반복 수가 적고 스레드 스케줄링 차이가 있어 API 전체 지연이 개선됐다고 주장하지 않는다. 확인한 개선은 반복 전체 DB 정리 제거와 이 조건의 파기 시간 감소다. 실제 맥미니의 데이터 규모·디스크·동시 요청·모델 대기 시간은 이 결과로 보증하지 않는다.

`before.json`과 `after.json`은 원시 요약이다. `offline_storage_probe.py`는 backend 디렉터리에서 실행하는 독립 로컬 점검 도구이며 임시 DB만 사용한다. 온보딩 해석·SAR 수치·시뮬레이션 계산 규칙은 이번 성능 수정에서 바꾸지 않았다.

## 병합 기준과 범위

새 동시성·파기 회귀 검사와 기존 전체 backend/tests 결과를 PR 본문에 기록한다. 실제 모델 품질, 실제 환자 행동, 운영 부하 한계 검증과 구분한다. GitHub Actions 워크플로는 이 저장소에 없어 서버 측 CI 통과로 표현하지 않는다. develop 병합 후 실제 서비스 배포는 별도 작업이다.
